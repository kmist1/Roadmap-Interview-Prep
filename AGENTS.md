# AGENTS.md — Senior iOS Interview Prep Roadmap

This file orients any LLM agent (or human) picking up work on `Interview_Prep_Roadmap.html`.

## What this is

A single self-contained HTML file — no build step, no dependencies — that renders an
interactive study roadmap for Krunal's Senior iOS interview prep (target: Apple).
It's structured as **3 chronological phases** (Foundation → Depth → Integration, ~12 weeks)
plus a 4th non-chronological **Apple Question Bank** column of company-tagged LeetCode
problems. Each phase contains **tracks** (topic areas); each track has a **checklist of
tasks** with per-task notes. Progress and notes persist across sessions.

Open the file directly in any browser — nothing to install. It's also deployable as a
free static site (see `DEPLOY.md`) and installable on a phone as a PWA.

## File structure

The **app is still one self-contained HTML file** (`Interview_Prep_Roadmap.html`) — no
build step, no dependencies, works offline when opened directly. As of the hosting work it
is now a full HTML document (`<!doctype html><html><head>…</head><body>…`) with a mobile
`viewport` meta and Apple/PWA `<meta>`/`<link>` tags in the head — needed so it renders
correctly on phones and can be "Add to Home Screen"-installed.

A few **sibling files exist only for hosting/PWA** (the app runs fine without them; the
links just 404 harmlessly when opened as a local file):
- `manifest.json` — web app manifest (name, colors, icons, `start_url: "./"`)
- `icon-192.png`, `icon-512.png`, `icon-180.png` — app icons (gradient + checkmark),
  generated by a throwaway node script (no image libs); regenerate at that size if changed
- `DEPLOY.md` — step-by-step GitHub Pages deployment + phone-install guide

Inside the HTML file:
- `<style>` block — dark theme, CSS custom properties for accent colors per track
- `<div id="app">` — mount point, fully rendered by JS (no server, no framework)
- `<script>` — one IIFE containing:
  - `DATA` — the entire content model (see below)
  - a `storage` abstraction (see Storage section)
  - render functions (`render`, `renderTrack`, `renderTaskRow`, `refreshProgress`,
    `attachListeners`, `init`)

## UI / layout (current)

The page is a **vertical accordion**, not the old side-by-side column board:
- A sticky-feeling header with the title, an **overall progress bar** (`#overall-fill` /
  `#overall-label`, aggregated across every task), and a row of **quick-jump chips** —
  one per phase, each scrolling to that phase's `<section id="phase-N">` and showing a
  live `done/total` count.
- Each phase is a `<section class="phase">` with a header (name, weeks, `done/total`).
- Each track is a **collapsible card** (`.track`). Clicking its `.track-head` toggles the
  `.open` class; the checklist drops down inline via the `grid-template-rows: 0fr → 1fr`
  animation trick (`.track-body > .inner` has `overflow:hidden`). Multiple tracks can be
  open at once; open state lives in the module-level `expanded` Set.
- `refreshProgress()` recomputes and updates every mini-bar/count, phase count, chip
  count, and the overall bar in place after any checkbox change (no full re-render).
- `render()` rebuilds the whole DOM from `state` (which `init()` preloads for all tracks
  via `Promise.all`) and honors the `expanded` Set, so a per-track **Reset** just calls
  `saveState(...)` then `render()` and the track stays open.

## Data model

```js
const DATA = [
  { phase: "Foundation", weeks: "Weeks 1-4", tracks: [
    { id: "f-swift", name: "Swift Language Fundamentals", color: "var(--accent-swift)",
      tasks: [
        { t: "Task description text", tag: "Swift" },
        ...
      ]
    },
    ...
  ]},
  ...
];
```

- **`phase`**: one of the 4 top-level columns rendered left-to-right in that order.
- **`weeks`**: display-only subtitle under the phase header.
- **`track.id`**: **must be globally unique** across the whole file — it's the storage
  key (`progress:<id>`) and the DOM lookup key. Existing ids use a `<phase-prefix>-<slug>`
  convention: `f-` (Foundation), `d-` (Depth), `i-` (Integration), `bank-` (Apple Question
  Bank). Follow this when adding a track.
- **`track.color`**: a CSS var, e.g. `var(--accent-swift)`. Define new accent colors in
  the `:root`-equivalent block at the top of `<style>` (search for `--accent-`) before
  referencing them. Pick a hex distinct from existing accents — there are ~20 already, so
  check the list before choosing.
- **`task.t`**: the task label shown to the user. For the Apple Question Bank, the
  convention is `"<LeetCode #>. <Name> (<Difficulty>)"`.
- **`task.tag`**: short category chip shown next to the label (e.g. `"Swift"`,
  `"Concurrency"`, `"Apple"`). Roughly one tag per track, reused across its tasks.

## Storage & persistence

Per-track state is one JSON blob per track: `{ done: [bool...], notes: [string...] }`,
stored under key `progress:<trackId>`.

The **Personal To-Dos** panel (a free-form, UI-editable list, separate from the study
roadmap and not counted in the overall/phase progress) is stored under a single key
`todos:general` as a JSON array of `{ id, text, done, ts }`. It's managed by
`loadTodos`/`saveTodos`/`addTodo`/`renderTodos`; user-entered text is HTML-escaped via
`esc()` before rendering. This is the one place users can add/delete items from the UI.
`renderTodos()` groups items **by calendar day** (via `dayInfo(ts)` → Today / Yesterday /
dated), newest day first, with open items sorted above done within each day; `ts` is the
grouping key and is backfilled on load for any legacy item missing it.

**Backup (export/import).** `exportData()` serializes `{ app, version, exportedAt,
progress: state, todos }` to a downloaded JSON file; `importData(text)` validates it,
confirms, then writes each track blob via `saveState` and replaces `todos` via
`saveTodos`, then re-renders. This is the current cross-device story (manual). There is
**no automatic cloud sync yet** — `localStorage` is per-device. A GitHub Gist + token
approach (or Supabase) was discussed as the next step; nothing is wired for it.

The `storage` object (top of the `<script>`) auto-detects environment:
- **Inside a Claude.ai artifact**: uses `window.storage.get/set` (the Claude artifact
  persistence API).
- **Standalone in a real browser** (downloaded and opened directly): `window.storage`
  doesn't exist there, so it falls back to `localStorage` under an `ios-interview-roadmap:`
  key prefix.

This means: **don't add direct `window.storage.*` or `localStorage.*` calls anywhere
else** — always go through the `storage.get`/`storage.set` wrapper, or the fallback
breaks.

`loadState()` backfills `done`/`notes` arrays with `false`/`""` if a track's task list
has grown since the state was last saved, so **it's safe to append new tasks to an
existing track** without wiping anyone's saved progress. It is **not** safe to reorder
or delete tasks from the middle of an existing track's array — indices are positional,
so that would silently reassign an old completion/note to a different task. If a task
needs to be removed, prefer leaving it in place and marking it (e.g. prefix the label
with "(retired)") over deleting the array entry, unless you're OK resetting that track's
progress.

## Adding content — checklist for an agent

1. **New task in an existing track**: append to that track's `tasks` array. Never
   insert/reorder/delete existing entries in that array (see persistence note above).
2. **New track in an existing phase**: add a new `{ id, name, color, tasks }` object to
   that phase's `tracks` array. Pick a unique `id` following the `<prefix>-<slug>`
   convention, and either reuse an existing `--accent-*` color that fits the topic
   family or define a new one.
3. **New phase**: add a new `{ phase, weeks, tracks }` object to `DATA`. Phases now render
   as **stacked vertical sections** (each an accordion of tracks), so any number of phases
   works fine — but each also gets a quick-jump chip in the header, so a very long list of
   phases makes that chip row unwieldy; consider whether a topic is really a new phase vs.
   a track within Depth.
4. Always validate the embedded JS after editing before treating the file as done:
   ```
   node -e "new Function(require('fs').readFileSync('Interview_Prep_Roadmap.html','utf8').match(/<script>([\s\S]*)<\/script>/)[1])"
   ```
   This only checks syntax, not runtime behavior — open it in a browser too if the
   change is nontrivial.

## Design constraints to preserve

- **Single file, no build step.** Keep all app logic/markup/style in
  `Interview_Prep_Roadmap.html`. Don't introduce a bundler, npm deps, or a framework — the
  point is "download and double-click to run." (The only sibling files are the optional
  PWA assets in File structure; they carry no app logic.) A React/SPA migration was
  explicitly considered and rejected — don't propose it again without a concrete new need.
- **Works offline.** The app itself makes no network calls; everything runs from local
  files + `localStorage`. If/when cloud sync is added, it must degrade gracefully offline
  (keep `localStorage` as the source of truth / cache).
- **No frameworks.** Vanilla JS/DOM, intentionally, to keep it a single portable file.
- Checklists open **inline as a dropdown/accordion** under each track (Krunal's explicit
  request, replacing the earlier bottom detail-panel and the side-by-side column board).
  Don't revert to a separate detail pane without asking.
- Each task row supports an optional note (collapsible textarea, autosaves ~500ms after
  typing stops) — preserve this when touching `renderTaskRow()` / `attachListeners()`.

## Open items / known limitations

- The study **roadmap** tasks/tracks are still edited only in the `DATA` source — no UI
  affordance to add them (a deliberate simplicity trade-off). The **Personal To-Dos**
  panel is the exception: it's fully add/edit/delete from the UI.
- `localStorage` is scoped per-browser-per-origin, so progress does **not** sync across
  devices/browsers. Mitigated for now by the **Export/Import** JSON buttons (manual
  transfer). Real cross-device sync (GitHub Gist + token, or Supabase) is the open
  follow-up Krunal asked about — not yet built.
- Deployment to GitHub Pages is documented in `DEPLOY.md` but not yet done (requires
  Krunal's GitHub account; `gh` CLI isn't installed on the dev machine).
